# prg - Public Repo Generator

**Turn a private development repository into a clean, public release history.**

`public-repo-generator` (`prg`) creates a new public repository from the
**real releases** of a private Git repository. It keeps the history that matters
to people looking at the finished project, while leaving the development diary
where it belongs: in the development repository.

> **Show the work. Not the dirty dishes.**

## Quick start

```bash
pipx install "git+https://github.com/east-van-ai/public-repo-generator.git"

# Shows instructions
prg

# Generates a new public repository from a dev repo
prg generate <source-repository> <destination-repository> --commit
```

## Why?

A development repository is a record of how software was built. It contains
AI-assisted iterations, deleted experiments, abandoned approaches, temporary
fixes, internal notes, development configuration, and thousands of small
working-state commits.

A public repository has a different job. It should show what you released, how
the project evolved, and what someone can use today. `prg` creates that public
view from your real release history.

### What it does

Suppose your private repository contains:

```text
development history
      │
      ├── experiments
      ├── abandoned work
      ├── branches
      ├── fixes
      └── releases
             │
             ▼
        v0.1.0
        v0.2.0
        v0.3.0
        v1.0.0
```

`prg` uses those release points to build a new repository:

```text
v0.1.0 ── v0.2.0 ── v0.3.0 ── v1.0.0
```

The resulting repository is a **real Git repository with real ancestry**, not
a collection of unrelated snapshots. Visitors can still inspect the evolution
of the project:

```bash
git diff v0.2.0 v0.3.0
```

Unlike orphan-commit snapshots, `prg` reconstructs releases as a connected Git
history. The resulting repository preserves meaningful ancestry between released
versions without exposing the private development history in between.

### Clean logs

This is what the generated repository looks like from the inside.

```text
$ git log --oneline --all --graph --format="%h %d %s %an <%ae> %ai"

* a450123 (HEAD -> main, tag: v1.2.1) v1.2.1 Jim Doe <jim.doe@example.com> 2026-06-03 12:00:00 -0700
* c691120 (tag: v1.2.0) v1.2.0 Jim Doe <jim.doe@example.com> 2026-05-21 12:00:00 -0700
* db90110 (tag: v1.1.0) v1.1.0 Jim Doe <jim.doe@example.com> 2026-04-10 12:00:00 -0700
* c80b100 (tag: v1.0.0) v1.0.0 Jim Doe <jim.doe@example.com> 2026-03-29 12:00:00 -0700
* abea031 (tag: v0.3.1) v0.3.1 Jim Doe <jim.doe@example.com> 2026-02-19 12:00:01 -0800
* c42f030 (tag: v0.3.0) v0.3.0 Jim Doe <jim.doe@example.com> 2026-02-19 12:00:00 -0800
* d80b020 (tag: v0.2.0) v0.2.0 Jim Doe <jim.doe@example.com> 2026-01-11 12:00:00 -0800
* c7a8010 (tag: v0.1.0) v0.1.0 Jim Doe <jim.doe@example.com> 2025-12-18 12:00:00 -0800
```

Every commit is a release. Each release is timestamped at noon. Two releases
cut on the same day sit one second apart, oldest first. Nothing else is in
there at all.

### When a version number is not enough

Sometimes a release deserves a sentence. Put an annotated tag beside it in your
private repo, named for the release it speaks for:

```bash
git tag -a prg-msg/v1.2.0 -m "v1.2.0 -- config files can be split across directories"
```

That release's public commit says the sentence instead of `v1.2.0`. Every other
release still says its version.

The marker tag stays private. So does the version tag's own annotation, which is
where six months of unguarded notes tend to live. Only the sentence you wrote on
purpose travels, and `prg inspect` shows it to you before it goes anywhere.

### What the history means

A repository generated by `prg` is deliberately a curated history. Each public
commit represents a released state of the project. It does not claim to
reproduce the exact sequence of development events, and that distinction is
intentional.

The public repository is:

> **a presentation of the work, not a record of how the work happened.**

The original development repository remains the authoritative record of
development. The generated repository is the authoritative public presentation
of the releases you chose to publish.

`prg` works particularly well when you want to publish an existing private
project, expose only selected releases, or keep development branches private.
It also lets you open a repository without losing Git ancestry.

## Basic usage

Start with a private repository containing tagged releases, then generate a
public repository from those releases.

```bash
prg generate <source-repository> <destination-repository> --commit
```

Dry run is the default. Without `--commit`, `prg` reports the plan it would
carry out and writes nothing.
